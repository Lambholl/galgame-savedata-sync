## 1. 目标与确认状态

M-002 交付可在 Windows 与 Android 之间使用的覆盖复制流程：选项目与方向，比较两端当前内容，预览操作，确认后备份并执行，查看逐项结果，必要时从目标端备份手工恢复。

用户已确认把默认备份保护提前到 M-002，让本阶段可覆盖真实存档。备份继续遵守 REQ-015：默认开启、可关闭、最近 3 次、目标端独立保存、可手工恢复，且不参与同步判定。镜像删除留 M-004。

本文件统一维护 M-002 的规则、协议、工作包与验收入口。用户已要求按序实现并在每个子包完成后提交；第 3 节作为工程实现基线，平台能力由对应包验证。验证写入继续使用合成目录。用户已取消 M-002 的 Android 10 实测，安卓实际运行验证使用 API 33 设备。

需求入口：[产品需求](../../.project-memory/requirements/product.md)、[验收标准](../../.project-memory/testing/acceptance.md)。当前实现入口：[模块状态](../../.project-memory/development/module-status.md)、[接口约定](../../.project-memory/architecture/api-contracts.md)。

## 3. 复制、备份与恢复约定

### 3.1 平台入口与备份位置

Windows `WindowsDirectoryAdapter.assertCacheIsolated` 已检查应用存储与已选根互不包含，`openFile` 提供原生流和变化复核，`locateNativeDirectory` 提供根/父身份检查。Android `SafPublicationBackend` 已有父目录/文档 ID/名称核实、`rw` 非预截断打开及 `Os.fstat` 常规 FD 身份检查。两者当前只实现新文件发布；这些入口可复用，覆盖和恢复须分别实现。

备份使用目标端应用私有持久目录：Windows 放在 `userData/backups/`，Android 放在 `Context.getFilesDir()/backups/`，均不用临时缓存。Windows 继续检查与所选根互不包含；Android 私有文件与 SAF 根分开处理，暂不增加第二次备份目录授权。备份页面展示实际位置及应用数据清除、卸载和手工删除对备份的影响。

### 3.2 当前扫描

扫描只存在于当前进程/会话，完成后保留最多 10 分钟，进程结束即失效。每次扫描生成新 `scanId`。

`SyncScanState` 表示 running/succeeded/failed/cancelled，包含 rootId/scanId、已读条目和字节进度；成功携带完整快照，失败可带部分条目及根级错误，取消没有成功快照。最多保留 32 个结果，到期清除；查询不延长期限。

- `SyncSnapshot`：`schemaVersion=1`、`scanId`、`deviceId`、`rootId`、`observedAt`、`entries`、`error`。
- 条目：`entryId`、相对路径段数组 `path`、`kind`、`sizeBytes`、`modifiedAt`、`sha256`、`error`。根本身不放进条目数组。
- 目录的 `sizeBytes`/`sha256` 恒为 null，枚举目录只用于同步。文件大小按原生流实测；未知大小/哈希用 null，读取失败保留 `OperationError`。
- 每个非根条目的父路径必须有对应目录条目。相同路径或相同 ID 不能重复；SAF 同名不同 ID 报 `name-conflict`，不能静默选一个。
- 根级 `error` 表示扫描未完成或失败，已读条目可供说明，整份结果阻止执行。成功的空数组表示真实空目录。
- 路径段保留原始名称，不改写大小写或 Unicode；快照可表示不能跨端创建的名称，计划将其列为冲突。平台路径与 URI 留原生层。

扫描最多 10000 条、深度 64、相对路径共 4096 个 UTF-16 码元，单个名称最多 255 个 UTF-16 码元。读取已有不可移植名称可报冲突，但不按该名称创建新文件。扫描截止时间 30 分钟、显式 IO 缓冲最多 64 KiB；超限或读取失败均返回完整失败状态。目录大小始终为 null，不做后代字节汇总。

### 3.3 比较计划

`createSyncPlan` 接收本次源/目标快照、`operation=copy|restore`、显式方向、项目 ID、新 `planId` 和 `shouldBackup`，输出只读 `SyncPlan`：固定的设备/根/扫描 ID、操作列表、问题列表、待传文件数/字节数及备份字节数。复制方向为 `windows-to-android|android-to-windows`；本机恢复为 `local-restore`，源是本机已验证备份、目标是本机当前扫描，且备份保护恒开启。比较器是纯 TypeScript，不执行 IO、哈希计算或历史查询。

| 当前条目 | 计划动作 |
| --- | --- |
| 源有目录、目标缺少 | `create-directory`，包含空目录 |
| 源有文件、目标缺少 | `create-file` |
| 两边都是文件、实测大小和 SHA-256 一致 | `skip`，日期不影响结果 |
| 两边都是文件、内容不同 | `replace-file` |
| 两边都是目录 | `skip`，继续处理独立列出的子项 |
| 仅目标有条目 | `keep` |
| 同路径类型不同 | `conflict`，整份计划阻止执行 |

任一快照失败、不可读条目、文件内容指纹未知、设备/根/方向不匹配、非法名称、名称等价冲突或资源超限，都阻止整份计划。名称冲突用 NFC 加小写的逐段键检查，原始名称仍用于显示和实际定位；两端仅大小写或 Unicode 规范形式不同的对应名称要求先处理，避免悄悄改名。最终名称等价和实际身份由目标平台再检查。

操作采用固定路径字典序，缺少的目录按深度排序、父目录先于后代。`issues` 非空时 `canExecute=false`，不能过滤冲突后执行其余部分。有效空计划或全部跳过/保留的计划显示“无需复制”。

### 3.4 确认与写入

确认绑定项目、源/目标设备 ID、rootId、两个 scanId、方向、备份设置和完整计划。更换上述任一输入后旧确认失效；计划只能在所属会话中执行一次。

1. 目标核实本机游戏配置、目录授权及身份，重查当前目标内容；源在准备归档时复核条目。归档实测长度和哈希须与确认计划一致。
2. 接收并完整校验 tar.gz 和所有文件。确认、扫描及归档接收阶段均不更改同步目录。
3. 开启备份且有覆盖时，先完整保存、校验全部将被覆盖的旧文件，提交有效清单后才进入写入。
4. 写入前再次检查父目录、条目身份和当前内容，变化时停止并报告 `source-changed` 或具体错误，重新扫描确认。目标独有条目保留。
5. 先创建缺少的目录，再逐文件新增/替换。写后回读长度和 SHA-256，通过后才报告该项成功；首次失败停止后续，已经成功的文件保留。

Windows 替换候选在同一目标卷准备，核实目标与父目录后发布；文件占用、身份变化或文件系统不支持时明确失败。Android 复用文档 ID、父目录及常规 FD 检查；有效备份（或明确关闭备份）及身份/内容复核完成后，使用非预截断 `rw` 句柄写入并设置最终长度。拒绝在身份检查前可能截断的 `w`/`rwt` 打开方式。提供者不能满足身份、回读或写入要求时返回 `unsupported-operation`。

流程按文件提交。任务锁不能阻止游戏持续写文件，同步前提示退出使用该存档的游戏；取消与写入竞争时返回实际结果，已经修改的目标不能记成未执行。

### 3.5 备份格式、轮换和恢复

每个本机项目/目标 rootId 保留最近 3 个有效备份轮次。有旧内容需要保护且完整清单提交成功时才产生轮次；纯新增、目录创建、全部跳过、备份关闭和提交前取消不增加轮次。备份完成后即使复制失败或取消，该轮仍保留。

备份使用独立 `schemaVersion=1`，每轮由随机 `backupId` 目录、连续 `f000001` 文件和清单组成。清单包含项目、目标设备/rootId、创建时间、原因 `copy|restore`，以及每个文件的原始相对路径、实测大小、哈希和可获得的原日期。主机路径与 SAF URI 不进入清单；恢复时重新解析稳定 rootId 和相对路径。

先写暂存轮次，逐文件同步落盘并读回，再原子提交清单。新轮可恢复前保留已有有效备份；第 4 轮有效后才淘汰最旧轮。活动恢复的输入轮次保持引用，释放后再轮换；轮换失败单独报告并暂时多留一轮。未提交轮次不进入可恢复列表，也不授权重放同步。

两端的私有所有权记录使用 `owner.json` / `round.json`，暂存清单提交为 `manifest.json`；淘汰先改为 `manifest.retired` 再清理已核实文件。列表提供轮次摘要和按需单轮清单，恢复前重新验证原文并持有引用。Windows 启动登记私有备份区，后续目录选择及读取均阻止它进入同步根；Android 使用应用私有 files 目录，与 SAF 授权目录分开。未完成轮次通过本机明确操作清理。

备份开关使用独立本机项目设置，缺省 `shouldBackup=true`，保持既有 `LibraryConfig` v1。关闭后每次执行确认显示“本次关闭覆盖前备份”，重新开启继续使用有效旧轮次。备份内容与索引只用于恢复、校验和轮换，不能成为同步比较基线。

手工恢复在目标本机操作：选择轮次，预览受影响文件和当前变化，确认后恢复。只写备份包含的文件，缺少的父目录会创建，其他条目保留；文件/目录冲突时阻止执行。恢复材料先完整验证，被覆盖的当前内容始终另建 `reason=restore` 的保护轮次，普通复制的开关不影响这一保护。当前文件与备份相同时跳过。恢复复用目标身份检查、写入/回读、容量预检和逐项结果。

重启后可查询有效备份；授权失效需重新选择目录。崩溃留下的暂存轮次只用于显式检查与清理，不当成已完成备份或自动续传任务。

### 3.6 HTTP 与本地桥

既有 `/v1/device`、`/v1/catalog`、`/v1/transfers/*` 的字段和非覆盖行为保持。新增 `/v1/sync/*` 使用独立 `schemaVersion=1` 和封闭 DTO；缺少能力或版本不符时提示更新，不能用旧接口降级执行覆盖。

| 入口 | 方法 | 职责 |
| --- | --- | --- |
| `/v1/sync/capabilities` | GET | 会话内查询扫描、覆盖、备份和恢复能力及固定预算 |
| `/v1/sync/scans` | POST | 核实本机 rootId，登记异步只读扫描 |
| `/v1/sync/scans/{scanId}` | GET / DELETE | 取状态/结果或取消，轮询不延长期限 |
| `/v1/sync/projects/{projectId}` | GET | 只读取得本机已保存项目的目录 ID 和目标端备份开关；不远程修改设置 |
| `/v1/sync/jobs` | POST | 接纳方向、扫描和确认计划，服务端复核本机快照、配置和操作集合 |
| `/v1/sync/jobs/{jobId}` | GET / DELETE | 查询实际任务或显式取消 |
| `/v1/sync/jobs/{jobId}/manifest` | GET / PUT | 获取已准备好的受限归档清单；上传方向由源在归档准备后单次提交清单 |
| `/v1/sync/jobs/{jobId}/content` | GET / PUT | 按方向提供仅一次原生 gzip 内容流 |

新增入口沿用 `x-sync-session-id`、严格 UTF-8/JSON、字节预算和 ID 检查。登记任务需核实保存的游戏映射和对端设备 ID；原生层逐段解析相对路径和根内引用。归档成员仍为 fileId，不直接拼成目标路径。

复制任务使用独立 `SyncJobRequest`：schemaVersion、jobId、sourceProjectId、targetProjectId 和完整 plan；jobId 等于本次 planId，plan.projectId 使用目标端项目 ID。确认后先登记任务，接收端保留本次确认及互斥，源再准备归档；上传清单由单次 PUT 提交并逐文件匹配计划的源引用/父目录/名称/日期/大小/哈希，随后才进入 2 分钟等待内容阶段。清单未提交时 GET 返回 null；无文件的计划直接执行目录/空计划分支，不提交清单或内容。登记、清单或内容回执丢失均只查询同 ID，不重放 POST/PUT。

下载方向的 Windows POST 先返回 preparing，原生源复核和归档准备完成后进入 ready；清单由 GET 取得，内容 GET 只领取一次。手机使用本机目标项目的备份开关，下载前合并检查缓存、备份和已知同卷的目标增量；完整接收并校验后重新核实目标并保护、写入。写入器借用手机确认时取得的名额及时间，持续传输期间仍须复核实际目标；本机处理期间的心跳只核对通信。Windows sender 的末次查询丢失可单独显示待确认，手机仍保留自己的实际写入结果；受保护写入和清理均不重放。

新同步客户端使用 `x-sync-device-id` 标记既有目录表连接中的设备；它与会话、项目关联和两端目录 ID 一并核对，不作为认证凭据。实际同步请求和进度可更新设备在线时间，避免把持续通信中的传输误记成断连。旧接口和现有扫描调用保持兼容。任务状态分开 sender/receiver、阶段和字节/文件计数；sender 的 sent 仅表示发送完成，目标是否成功仍核对 receiver 的完整 `SyncApplyResult`。预览、清单与结果按需分别查询，避免把两份快照与结果合并到同一控制响应。

备份设置、列表与本机恢复通过有限 IPC/Capacitor 桥提供，本阶段不开放远端任意恢复/删除入口。原生任务持有文件、句柄和取消控制，JS 只发确认、取状态及取消；界面卸载不取消任务。文件非空时复用既有 tar.gz/USTAR 规则；仅目录或无需写入的任务走无内容分支，不创建虚构文件或空归档。

### 3.7 预算、期限与失败结果

- 每端一个会改目标的活动任务，旧传输、新复制及本机恢复共享互斥；清理未完成时不接纳另一写任务。
- 待传文件最多 1024 个、单文件 256 MiB、原文合计 1 GiB，压缩体/缓存沿用 `BATCH_LIMITS`/`BATCH_RESOURCES`。备份文件独立采用同一文件数/单文件/原文限制，超过任一预算提前拒绝整份计划。
- 计划/控制 JSON 最多 8 MiB；扫描数量/深度另按 3.2 限制。
- 容量预检包含接收缓存、目标卷候选/最终文件增量、完整旧内容备份及轮换前暂时多留一轮的峰值，同卷开销相加。提供者余量未知保持未知，实际写入继续检查；不能提前删除有效备份换空间。
- 总期限 30 分钟、等待内容 2 分钟、网络无进展 60 秒、准备好等待确认及终态保留均最多 10 分钟。重启、会话改变和到期后重扫当前目录，不恢复写任务。
- 分别报告阶段、逐项成功/失败/取消/未执行/待确认、备份及清理状态。`sender sent` 只是已发送，目标成功依据 receiver 回读结果。
- 回执丢失只查询，不重放内容或写入。任务不可查询时标记待确认并提供重读当前目录入口。

- 退出条件：复制和恢复的正常、取消、变化、备份失败、部分成功及结果未知流程均有明确输入输出；备份位置和 SAF 可行性调查有结论；需要用户选择的规则完成确认。
- 边界：本包只写设计；未解决的提供者能力问题明确交给平台包验证，不能以设计推断代替真机证据。

### WP-017 共享扫描模型与纯比较计划

- 依赖：WP-016。
- 范围：`apps/shared/src`；实现本次扫描、差异操作、备份/恢复公开状态及结果的 DTO、校验和纯比较规则。
- 交付：以当前快照和显式方向生成确定的计划，区分新增、覆盖、跳过、保留、空目录与阻塞冲突；为后续平台包提供一致的数据定义。
- 退出条件：同大小异内容、同内容异日期、空文件、未知属性、目标独有条目、类型冲突及扫描失败能按约定表示；历史任务不改变结果。
- 边界：不做 IO、计算文件哈希或存储文件索引；Java 按同一格式适配原生输入输出，比较规则以共享层为准。

### WP-018 已有项目映射与手动连接补齐

- 边界：已有行为通过场景复核即可，不重写页面或存储；自动发现、自动重连与 ID 迁移归 M-003。需要配置迁移时补迁移和回退设计。

### WP-019 Windows 当前扫描与内容指纹

- 退出条件：嵌套与空目录、同大小不同内容、链接/越界、源变化、超限和取消可区分；扫描不修改源，浏览不触发目录大小汇总，快照随任务释放。
- 边界：只读；不负责比较、备份、传输或目标发布。协议声明由 WP-016/WP-017 提供，本包只实现 Windows 扫描服务。

### WP-020 Android SAF 当前扫描与内容指纹

- 边界：普通本地只读扫描，不加保活，不判断前后台或处理切后台后的成败；保留显式取消、期限和实际读取错误，实际传输编排留方向包。

### WP-021 Windows 独立备份与轮换

- 退出条件：可独立读回并核对备份；备份区不进入同步扫描；备份创建或校验失败时不能放行覆盖；新备份确认可恢复前保留已有有效备份，空间不足明确失败。

### WP-022 Android 独立备份与轮换

- 退出条件：目标真机验证备份读回、最近 3 次保留、重启后的手工查询、权限失效与失败停止；容量未知与不足分别报告；备份和同步目录不互相包含。
- 边界：备份位置由 WP-016 明确；遇到 SAF 能力差异先验证或拆包。实际恢复写入由 WP-024 负责。

### WP-023 Windows 目录创建、受保护覆盖与恢复写入

- 范围：桌面主进程新建/替换适配、逐项结果及本机恢复调用；复用 `new-file-publisher.ts` 的已验证边界。

### WP-024 Android SAF 目录创建、受保护覆盖与恢复写入

## 5. 依赖与执行顺序

1. WP-016 先细化并确认规则；WP-017 提供共享数据与比较器，WP-018 补已有配置行为。
2. Windows 路径：WP-019 扫描、WP-021 备份，再做 WP-023 受保护写入和恢复。
3. Android 路径：WP-020 扫描、WP-022 备份，再做 WP-024 受保护写入和恢复。
4. WP-025 先串通 Android → Windows，并完成通用新增协议接入；WP-026 接入另一个方向。
5. WP-027/WP-028 接入各自平台页面；WP-029 汇总真机和产品验收。

依赖允许先验证单个平台或单个方向；它不授权并行 Agent。平台备份与写入包可通过原生合成夹具先验证，方向编排包再通过实际 LAN 验证；界面包做最终可操作流程验收。

## 6. 验收与开放条件

| 验收组 | 必须观察到的结果 | 主责包 |
| --- | --- | --- |
| 配置和身份 | 多项目重启保留；手动改 IP 保留映射；另一设备不能套用旧配置；任务不随当前选择漂移 | WP-018 |
| 当前状态比较 | 同大小异内容标为覆盖；内容相同但日期不同可跳过；改变历史记录不改变计划；未知/不可读/空目录分开 | WP-017、WP-019、WP-020 |
| 复制规则 | 两个方向都能新增嵌套文件和空目录、覆盖差异文件、跳过相同文件、保留目标独有条目；类型冲突按确认规则处理 | WP-023 至 WP-026 |
| 备份和恢复 | 默认开启、可关闭；备份包含对应旧内容；第 4 次轮换后保留最近 3 次；重启可查并手工恢复；恢复失败如实报告；备份不参与比较 | WP-021 至 WP-024、WP-027、WP-028 |
| 变化及失败 | 确认后源/目标变化、权限失效、断网、空间不足或未知、取消、回执丢失、部分成功均有明确结果；备份失败阻止默认覆盖 | 平台包、WP-025、WP-026 |
| UI 和生命周期 | 两端预览、手机发起、清楚的方向/备份/进度/逐项结果；仅传输验收后台继续、Activity 重建查询原传输、显式取消与清理；目录不汇总大小 | WP-027、WP-028 |
| 平台和资源 | Windows、Android API 33 的实际目录/提供者；归档保持原有资源预算，备份和恢复峰值容量另有证据 | WP-029 |

验证沿用当前规范：默认不新增或扩写自动化测试；实现包先做针对性实际运行，再运行受影响工程检查及必要的既有回归。`pnpm check` 检查文本、格式、lint、类型和双端构建；Android 原生改动补 `pnpm android:test` 与真机操作。依赖变化才触发相应审计；新增测试需说明场景后另行确认。

M-001 的 1 GiB 结果继续作为已有传输基线；M-002 要重新核实覆盖、备份、恢复产生的空间峰值和受影响的资源行为。首个真实存档覆盖版本必须具备默认备份和手工恢复的完整验收；关闭备份入口遵守最终确认规则。文件系统或 SAF 提供者不满足安全写入约定时，明确报告该环境不可用。

## 7. 拆包与恢复入口

共享协议、归档格式、备份格式、提供者能力、配置迁移或资源预算发生超出包范围的变化时，先更新 WP-016 约定与受影响依赖，再决定是否新增工作包。超过已确认归档限制的多批任务、崩溃残留恢复和额外提供者支持不顺带混入当前包。

开工、阻塞、重要检查点与完成时同步[索引当前工作](../../.project-memory/INDEX.md)、[工作包登记](../../.project-memory/development/work-packages.md)和对应验收状态。M-002 的规则、协议及分包统一在本文件更新，具体当前包以登记表为准。
