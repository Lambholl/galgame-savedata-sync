## 2. 能力与数据边界

| 层 | 设计职责 | 限制 |
| --- | --- | --- |
| 共享模型 | 设备描述、目录引用、条目元数据、能力、任务进度、错误与传输回执 | 使用纯 TypeScript 模型，不导入 Electron、Node 文件 API 或 Android 类型；内容不通过 JS 桥传递 |

| Windows HTTP | 描述设备/会话、读取登记目录、准备/发送归档、接收归档、查询/取消任务 | WP-004/005 编排归档及发布；范围限于已登记根与获写授权的独立夹具 |
| Android HTTP | WP-006 原生编排双向归档、网络、校验及 SAF 发布，向 JS 发出进度和实际结果 | 复用 WP-013/WP-010；不传 Base64；持续通知/dataSync 前台服务保持活动任务，切后台不取消，界面重建查询同一任务 |
| 验证界面 | 展示源/目标、当前读取时间、真实属性、连接及任务结果 | antd 与 antd-mobile 分别适配；文件夹大小显示“—” |

目录引用与地址分离。Windows 和 Android 均在安装内生成并保存稳定 deviceId；目录引用以稳定 ID 和本地配置为准，连接地址可以修改。M-001 只验证身份读取和本地保存，设备关联与换址迁移的完整流程由 M-002/M-003 完成。

条目采用平台不透明 entryId 和显示名称，访问目录时使用 entryId，不用显示名称拼装路径。目录为空、条目不存在、授权失效、读取失败分别表达。未知文件大小用 null，空文件用 0；文件夹大小固定 null。修改日期是条目自身的时间戳，未知用 null，不参与方向判断。

列目录只查询当前层；用户展开时再查下一层，不为文件夹大小遍历后代。提供者能力区分支持、不支持和未知，实际操作结果优先于预先声明。Android 是否保留原修改日期、是否支持目录级原子替换，取决于提供者能力。

## 3. 文件往返流程

### 3.1 读取与连接

1. 用户在 Windows 本机和 Android 系统选择器分别选择测试目录；取消选择不清空既有有效引用。
2. Windows 主进程显式启动测试 HTTP 服务并显示监听地址、实际端口和状态；本期不引入 mDNS。端口冲突必须显示失败，服务随应用退出释放。
3. Android 前台通过手动 IP/端口读取设备描述，确认协议版本，再读取 Windows 已登记根目录的当前层条目。
4. 本地授权与远端地址分开保存。Android 重启后重新核实授权；授权失效时显示错误并要求重新选择。

### 3.2 Android → Windows

1. 用户选择 Android 显式文件集合及 Windows 已有目标父目录/新文件名映射，生成本次 transferId；原生层私有暂存源原文并实测长度/哈希，生成稳定 tar.gz 及清单，核实可观察源变化。
2. POST /v1/transfers/uploads 先登记清单和目标，Windows 检查会话、写授权、冲突、资源和单次 ID；201 表示任务已登记。
3. PUT content 发送唯一归档；Windows 私有暂存、校验完整压缩体及所有原文后才逐项非覆盖发布。202 表示校验和发布在后台进行，完成后还要回读目标；首次发布失败停止后项并保留实际结果。
4. 通过 GET 任务状态取得逐文件终态。响应丢失时查询并核实，POST/PUT 不重放；目标状态未知时重新读取目标。字段、期限及错误详见批量协议。

### 3.3 Windows → Android

1. POST /v1/transfers/downloads 指定 Windows 文件集合，服务异步准备私有原文快照和归档，ready 后 GET manifest；清单和原文只用于本次任务。
2. Android 验证清单、本地已有目标映射和写授权，再 GET content；先完整校验归档及全部原文，后调用 SAF 发布，不将归档路径直接展开至目标。
3. SAF 新建后核实实际名称、内容/EOF 和最终条目，逐文件反馈；遇到改名、同名歧义，或提供者无法保证不改写已有文件时，拒绝或报告待确认。排他创建要先确认平台能力。
4. Windows 的 sender sent 表示发送完成，手机 receiver succeeded 才表示目标全部发布。失败或取消时只清理本次确知新建的未完成项，保留已成功文件与原有文件，列出残留。

### 3.4 中断与结果

批量协议区分 sender/receiver：sender 的 sent 表示本机发送完成，receiver 的 succeeded 才表示目标发布完成，双方均可失败、取消或待确认。running 阶段包括 preparing/ready/awaiting-content/transferring/verifying/publishing/cleaning，分开源读取、归档传输、原文校验和已发布字节；未知总量不计算百分比。逐文件结果可为成功、失败、取消、未尝试或待确认；完整约束见批量协议第 6 节。

Android 界面不可见时不新增任务，已有传输由持续通知/dataSync 前台服务持有并继续；Activity 暂停或销毁不会取消。用户显式取消时关闭本地流，并请求 Windows 取消本次任务。取消与提交竞争时，以可核实的实际终态为准；已经发布的文件会保留，确认不了时显示待确认。Windows 暂存和任务状态限定本次会话，到期清理，不保存长期传输记录。服务重启后查询不到旧任务时，重新读取当前目录核实；不要根据旧状态自动覆盖或续传。

手机与电脑在同一局域网进行 HTTP 验收。ADB 用于安装调试包、查看日志及检查运行状态；实际文件传输走局域网 HTTP，不使用 adb push/pull、端口转发或 reverse。持续通知前台服务只承接用户已发起的活动传输，没有自动后台同步、定时/开机调度或旧任务重放。

## 5. 验证与完成条件

- 针对性检查优先：共享模型、Windows 临时目录与 HTTP 集成、Android 原生编译与提供者行为；功能验证优先 lint、编译、ADB 实操与截图；默认不新增或扩写自动化测试，已有最小检查可运行，具体遵守当前测试规范。
- 受影响实现包完成后执行 pnpm check；Android 原生有改动时补原生构建；新增或变更依赖时执行现有 npm、Android 依赖与工具链安全检查。网络或解析失败时，审计保持未通过。
- Android 真机检查前准备 ADB；Windows 本地实现和 Android 原生构建无需连接设备。用户开启调试并确认设备授权后，才按对应验证范围安装和写入合成夹具。
- 设备组合至少包含 API 29 真机及一个较新 Android 版本真机；只有一台设备时可先验证该设备，未覆盖的平台继续标记为缺口。模拟器只补充兼容性检查。
- 用合成空文件、中文/空格文件名、嵌套目录和大于单次缓冲区的文件验证，不将真实存档作为故障注入材料。
- 具体场景见[测试用例](../../.project-memory/testing/test-cases.md)。目录读取与 HTTP 往返成功属于 M-001 的验证结果，覆盖复制、镜像、备份、自动发现和产品级验收仍为 pending。
- M-001 完成条件：共享模型、双端读取、归档、目标发布、HTTP 和界面均实现并检查通过；目标真机验证通过；双向内容与预期 SHA-256 一致；失败和取消如实返回，前台传输与不递归统计目录大小成立；规模资源证据补齐后形成结论。

## 6. 拆分与恢复规则

出现以下任一情况，停止扩大当前包，先在工作包登记中拆分并更新依赖：

- 同一包需要同时修改共享协议和两个平台的核心行为，且无法分别验证。
- SAF 提供者差异要求独立的能力协商、最终写入或残留恢复设计。
- 上传、下载或生命周期验证无法在同一包给出明确结果：按方向或生命周期边界拆包。
- 发现实现必须引入新依赖、变更持久配置格式，或改变既有产品范围；先记录影响和验证方案，需要改变已确认需求时再取得确认。
- 包内缺少设备时，只推进不依赖设备的实现与自动检查；将真机验收保持 pending，不把缺少证据标成通过。

新编号从当前最大编号之后分配。保留原包范围、已完成部分和剩余交接，新包只接收明确拆出的范围；同一交付物只写在一个包。每个包启动、阻塞、检查点及完成时更新 INDEX 与登记表。完成时先更新实现事实与证据，再调整工作包状态；提交 Git 仍需单独授权。

M-002 已形成分包草稿，具体规则、协议和兼容策略由 WP-016 细化确认。M-003/M-004 仍为拆分方向，进入时再细化工作包；备份保护先于真实存档覆盖开放。
