## 背景

0.x 阶段不保留兼容代码：落盘格式、协议字段和接口变化时直接换成新的，读到其他版本按读不懂的数据处理。电脑端把文件改名保留后用默认值启动，Android 直接删除这项数据；Android 的设备 ID 重新生成后，对端要重新添加本机。

1.0 起用户的游戏配置、目录登记和备份要跨版本保留，上面的处理在版本升级或降级时会丢数据。

## 决策

### 发布

1. 下一个发布版本是 1.0.0，不另发候选版。打包产物、升级路径和有风险的回归点在发布前于本地验证完。
2. GitHub Actions 发布工作流只创建草稿 Release。工作流失败时删除 tag，修复后重新打 tag；删除和重打 tag 都要维护者同意。

### 版本号

3. 1.x 按下表升级版本号：

| 版本段 | 何时升级 | 两端互通 |
| --- | --- | --- |
| 补丁（1.0.x） | 只修缺陷，不改落盘格式、`PROTOCOL_VERSION`、`/v1/sync/capabilities.schemaVersion` 和控制消息版本 | 同一次版本下的不同补丁版本可以互连 |
| 次版本（1.x.0） | 增加功能；可以改落盘格式（必须带自动迁移），可以升协议或能力版本 | 协议或能力版本变了时两端要一起更新，发布说明写明 |
| 主版本（x.0.0） | 旧数据无法自动迁移，例如不再能恢复上一主版本写的备份 | 按发布说明处理 |

### 落盘格式

4. 兼容范围包括电脑端的 `identity.json`、`directories.json`、游戏库配置、`backup-settings.json`、`backup-library.json`、服务端口设置、界面偏好、`SyncJobState`，Android 上对应的存储项，以及备份清单和备份文件夹结构。各格式当前的 `schemaVersion` 见[接口约定](../architecture/api-contracts.md)和两端平台层文档。
5. 1.0 的格式是基线，0.x 的数据不迁移，按读不懂的数据处理，发布说明写明。
6. 读到旧版本时按版本逐级迁移到当前版本再写回；迁移失败按读不懂的数据处理。
7. 读到比当前版本新的数据时不删除、不写回，提示升级应用；这项数据在本次运行中不可用。界面表现在实现时确定。
8. 内容损坏的数据沿用现有处理：电脑端改名保留后用默认值，Android 删除后用默认值。
9. 改落盘格式要维护者同意，同时写迁移和长期测试，见[测试约定](../standards/testing.md)。

### 备份和设备 ID

10. 1.0 起写入的备份在整个 1.x 内都能列出和恢复。
11. 设备 ID 只在首次启动或数据损坏时生成，版本升级不重新生成。

### 协议

12. 两端的 `PROTOCOL_VERSION`、`/v1/sync/capabilities.schemaVersion` 和控制消息版本必须相同，不做版本协商。版本不同时沿用现有处理：发现列表显示版本不同，连接和创建任务前提示更新两端。
13. 协议和能力版本只在次版本升级，升级要维护者同意。

## 原因

- 备份是用户找回存档的唯一途径，所以兼容等级最高。
- 设备 ID 变了，对端保存的设备和游戏关联全部失效，要重新添加本机。
- 两端从同一个 tag 一起发布，用户同时更新两台设备的成本低；版本协商要为每个协议版本保留旧的编解码分支，对两台设备之间的工具不划算。
- 发布脚本 `scripts/app-version.mjs` 不认带 `-` 的预发布 tag；发布前的检查都能在本地完成，工作流失败只影响草稿 Release。

## 影响

### 正面影响

- 升级应用后游戏配置、目录授权、设备关联和备份都保留。
- 降级或旧版本读到新数据时不会删掉它。

### 负面影响

- 每次改落盘格式都要写迁移和对应的长期测试。
- 协议或能力版本升级时，两端必须一起更新才能连接。
- 从 0.x 升级到 1.0 时游戏配置和目录登记会重置，要重新添加游戏和设备。

## 替代方案

| 方案 | 优点 | 缺点 | 结果 |
| --- | --- | --- | --- |
| 协议版本协商，兼容相邻版本 | 两端不必同时更新 | 每个版本都要保留旧编解码分支和对应测试 | rejected |
| 先发 0.9.0 候选版观察一段时间 | 有真实用户使用后再定格式 | 发布前的验证都能在本地完成，候选版只是推迟基线 | rejected |
| 1.0 迁移 0.x 数据 | 0.x 用户升级后不用重新添加 | 0.x 的格式变动多次，迁移代码只用一次 | rejected |
