## 1. 平台入口与备份位置

Windows `WindowsDirectoryAdapter.assertCacheIsolated` 检查应用存储与已选根互不包含，`openFile` 提供原生流和变化复核，`locateNativeDirectory` 提供根/父身份检查。Android `DirectoryPublicationBackend` 核实父目录、文档 ID 和名称，用不预截断的 `rw` 打开，并用 `Os.fstat` 检查常规文件描述符的身份。复制和恢复的写入复用这些检查。

备份使用目标端持久目录，不用临时缓存。Windows 放在备份库（默认是数据根下的 `backups`，见 [Windows 平台层](windows.md#7-配置与路径边界)），检查与所选根互不包含，备份页有按钮打开这个文件夹。Android 放在应用专属外部目录 `Android/data/<包名>/files/backups/`，不需要目录授权，用户可以直接管理；Android 10 还能选中存储根或 `Android/data`，所以选择目录时拒绝与备份目录互相包含的同步根。备份页面展示实际位置，并说明可以直接删除，卸载或清除数据会一并删除。

两端每份备份都是 `<游戏名>/<UTC 时间>/` 文件夹，内含 `backup.json` 和按原路径保存的 `files/`，不打包。用 13 个游戏的真实存档实测（文件 7–502 个，每个游戏 0.18–102 MB），tar.gz 后是原大小的 7%–98%，中位约 60%，合计 178 MB 压到 41 MB，电脑上压缩都不到 1 秒。默认保留 3 份时，13 个游戏也只省约 400 MB，换不来放弃直接查看、单独取文件和损坏只影响单个文件的代价，也不值得为恢复重写读取流程。

## 2. 当前扫描

扫描只存在于当前进程/会话，完成后保留最多 10 分钟，进程结束即失效。每次扫描生成新 `scanId`。

`SyncScanState` 表示 running/succeeded/failed/cancelled，包含 rootId/scanId、已读条目和字节进度；成功携带完整快照，失败可带部分条目及根级错误，取消没有成功快照。最多保留 32 个结果，满时丢掉最旧的，到期清除；查询不延长期限。

- `SyncSnapshot`：`schemaVersion=1`、`scanId`、`deviceId`、`rootId`、`observedAt`、`entries`、`error`。
- 条目：`entryId`、相对路径段数组 `path`、`kind`、`sizeBytes`、`modifiedAt`、`error`。根本身不放进条目数组。
- 目录的 `sizeBytes` 恒为 null，枚举目录只用于同步。扫描只列目录、读取元数据；Android 提供者不报大小的文件读一遍计数。未知大小或日期用 null，读取失败保留 `OperationError`。
- 每个非根条目的父路径必须有对应目录条目。相同路径或相同 ID 不能重复；SAF 同名不同 ID 报 `name-conflict`，不能静默选一个。
- 根级 `error` 表示扫描未完成或失败，已读条目可供说明，整份结果阻止执行。成功的空数组表示真实空目录。
- 路径段保留原始名称，不改写大小写或 Unicode；快照可表示不能跨端创建的名称，计划将其列为冲突。平台路径与 URI 留原生层。
- 任意层级名为 `.nomedia` 的普通文件不进入快照（共享包 `isUnsyncedFileName`，Android `SyncScanner.NOMEDIA_NAME`），所以不进入计划、写入前备份、手动备份和本机恢复，删除多出的条目和恢复后它仍然留在目标里。它是各设备自己的相册设置，见 [REQ-026](../requirements/product.md#2-需求清单)。名称精确匹配，`.NOMEDIA` 照常同步。电脑端扫描另跳过写入候选文件（[Windows 平台层](windows.md)第 11 节）。

扫描最多 10000 条、深度 64、相对路径共 4096 个 UTF-16 码元，单个名称最多 255 个 UTF-16 码元。读取已有不可移植名称可报冲突，但不按该名称创建新文件。扫描截止时间 30 分钟、显式 IO 缓冲最多 64 KiB；超限或读取失败均返回完整失败状态。目录大小始终为 null，不做后代字节汇总。

## 3. 比较计划

`createSyncPlan` 接收本次源/目标快照、`operation=copy|restore`、显式方向、项目 ID、新 `planId`、`shouldBackup` 和 `shouldDeleteExtras`，输出只读 `SyncPlan`：固定的设备/根/扫描 ID、操作列表、问题列表、待传文件数/字节数及备份字节数。待传字节统计本次写入文件；备份开启且计划有写入时，备份字节统计目标目录的全部文件，包括未变化和仅存在于目标的文件。复制方向为 `listener-to-dialer|dialer-to-listener`（ADR-0004）；本机恢复为 `local-restore`，源是本机已验证备份、目标是本机当前扫描，备份保护恒开启，`shouldDeleteExtras` 固定为 true（删除目标目录多出的文件与空目录）。比较器是纯 TypeScript，只用本次快照，不执行 IO 或历史查询。

| 当前条目 | 计划动作 |
| --- | --- |
| 源有目录、目标缺少 | `create-directory`，包含空目录 |
| 源有文件、目标缺少 | `create-file` |
| 两边都是文件、大小相同、修改日期都已知且相差不超过 2 秒 | `skip`；2 秒容差覆盖 FAT 类文件系统和 SAF 的秒级精度 |
| 两边都是文件、大小或修改日期不同，或修改日期未知 | `replace-file` |
| 两边都是目录 | `skip`，继续处理独立列出的子项 |
| 仅目标有条目 | `keep`；`shouldDeleteExtras` 为 true 时为 `delete-file` 或 `delete-directory` |
| 同路径类型不同 | `conflict`，整份计划阻止执行 |

任一快照失败、不可读条目、文件大小未知、设备/根/方向不匹配、非法名称、名称等价冲突或资源超限，都阻止整份计划。名称冲突用 NFC 加小写的逐段键检查，原始名称仍用于显示和实际定位；两端仅大小写或 Unicode 规范形式不同的对应名称要求先处理，避免悄悄改名。最终名称等价和实际身份由目标平台再检查。

操作采用固定路径字典序，缺少的目录按深度排序、父目录先于后代。`issues` 非空时 `canExecute=false`，不能过滤冲突后执行其余部分。有效空计划或全部跳过/保留的计划显示“无需复制”。

## 4. 确认与写入

确认绑定项目、源/目标设备 ID、rootId、两个 scanId、方向、备份选择、删除设置和完整计划。更换上述任一输入后旧确认失效；计划只能在所属会话中执行一次。

任务分备份、传输、写入三步，备份和传输同时进行。

1. 目标核实本机游戏配置、目录授权及身份，重查当前目标内容；源在准备时复核条目。
2. 接收端登记任务后立即开始备份：开启备份且有写入时，保存目标目录的全部文件，包括未变化、目标独有、嵌套和空文件；复制前后核对来源的大小和修改日期，复制出的文件保留来源的修改日期，提交有效清单后才进入写入。
3. 备份期间接收内容：发送端按计划写文件的顺序边读边打包为 tar.gz，读取前后核对每个文件的大小和修改日期，被改动时报 `source-changed`；接收端边收边解包到私有目录，成员名称、大小、顺序或 gzip 的 CRC、长度不对时报 `invalid-archive`。确认、扫描、备份及接收阶段均不更改同步目录。内容没收齐时任务失败，一项都不写；备份先失败时接收端停止接收。
4. 备份完成且内容收齐后，重新核对目标目录；逐个写入前再次检查条目身份、大小和修改日期，变化时停止并报告 `source-changed` 或具体错误，重新扫描确认。没有选择删除时目标独有条目保留。
5. 先创建缺少的目录，再逐文件新增/替换，最后执行删除。写入时核对字节数，写完把目标文件的修改日期设为来源的（Android 经 SAF 写入时设不了，保留写入时的日期，下次比较仍显示不同）；首次失败停止后续，已经成功的文件保留。

Windows 替换候选在同一目标卷准备，核实目标与父目录后发布；文件占用、身份变化或文件系统不支持时明确失败。Android 复用文档 ID 和常规文件描述符检查，不列父目录；有效备份（或明确关闭备份）及身份复核完成后，使用非预截断 `rw` 句柄写入并设置最终长度。拒绝在身份检查前可能截断的 `w`/`rwt` 打开方式。提供者不能满足身份或写入要求时返回 `unsupported-operation`。

流程按文件提交。任务锁不能阻止游戏持续写文件，同步前提示退出使用该存档的游戏；取消与写入竞争时返回实际结果，已经修改的目标不能记成未执行。

## 5. 备份格式、轮换和恢复

每个本机项目保留最近若干个有效备份轮次，份数是备份库的一个设置（1–4096，默认 10），作用于每个游戏；写入前备份（`copy`、`restore`）与本机手动备份（`manual`）平级轮换。传输计划选了写入前备份、计划有写入且目标目录存在文件时，或用户触发本机手动备份且当前目录存在文件时，完整清单提交成功才产生轮次；纯新增传输也会备份目标目录的当前内容。没有写入、目录没有文件或提交前取消不增加轮次；计划没选备份时不产生传输前的备份。备份完成后即使复制失败或取消，该轮仍保留。

备份使用独立 `schemaVersion=1`，每轮由随机 `backupId` 目录、连续 `f000001` 文件和清单组成。清单包含项目、目标设备/rootId、创建时间、原因 `copy|restore|manual`，以及每个文件的原始相对路径、实测大小和可获得的原日期；旧清单的文件项带 `sha256` 时照常读取，哈希值丢弃。主机路径与 SAF URI 不进入清单；恢复时重新解析稳定 rootId 和相对路径。

先写暂存轮次，逐文件复制并落盘，再原子提交清单。新轮可恢复前保留已有有效备份；新轮有效后才淘汰超出份数的最旧轮。活动恢复的输入轮次保持引用，释放后再轮换；轮换失败单独报告并暂时多留一轮。未提交轮次不进入可恢复列表，也不授权重放同步。

两端的备份文件夹结构相同，便于迁移。Windows 启动时登记备份区，后续目录选择及读取均阻止它进入同步根。列表提供轮次摘要和按需单轮清单，恢复前重新验证原文并持有引用。

备份文件夹允许用户随时改动，所以不做所有权校验，每次按实际目录读取：写入时清单放在 `in-progress.json`，全部落盘后原子改名为 `backup.json`；删除时先改回 `in-progress.json`。文件缺失或大小不符的备份和未提交的一样显示为不完整，可以清理，不能恢复。Windows 轮换时它们不计入保留份数，也不删除；Android 轮换时它们也占份数，超出时先删它们，再删最旧的完整备份，没超出不检查文件。恢复时写入核对字节数，轮换只看文件在不在和大小，不读内容。Android 删除备份和移除游戏不检查文件。两端清理或轮换失败后都不挡新备份，删不掉的备份下一次轮换再删。电脑作为目标和 Android 恢复时提示“临时文件未清理”，Android 作为传输目标时不提示。读不懂的文件夹和无关文件直接忽略，整个 `backups` 被删后自动重建。备份设置放备份区外的 `backup-settings.json`（Android 内部目录，Windows 的数据目录），不随备份文件夹丢失。Android 外部存储不可用时开启备份的写入被挡住，关闭备份的写入不受影响。

列表只显示 deviceId、projectId 和 rootId 都对得上的备份。不做导入功能：把另一台设备的备份复制过来不会显示，迁移时手动取用 `files/` 里的文件。

是否在写入前备份由发起传输的设备在传输页按次选择：开关在比较结果的工具栏上，与“保留/删除”开关并列，只在目标有文件时出现，进入传输页、翻转方向和重新扫描后回到关闭，不保存。确认时选择随计划（或 `sync.confirm` 的 `shouldBackup`）交给执行方，执行方用同一批快照重新生成计划，目标端不拿本机设置核对这个选择。保留份数存在备份库的 `backup-settings.json`（`{ schemaVersion: 4, keepCount }`），归存放备份的设备，不随传输交换。开始传输前不因没选备份另加确认；没选备份时被覆盖和删除的文件直接丢弃，写入中断后重新传输。备份内容与索引只用于恢复、校验和轮换，不能成为同步比较基线。

手工恢复在目标本机操作：选择轮次，预览受影响文件和当前变化，确认后恢复。只写备份包含的文件，缺少的父目录会创建，其他条目保留；文件/目录冲突时阻止执行。恢复材料先完整验证，被覆盖的当前内容始终另建 `reason=restore` 的保护轮次，普通复制的开关不影响这一保护。当前文件与备份相同时跳过。恢复复用目标身份检查、写入、容量预检和逐项结果。

重启后可查询有效备份；授权失效需重新选择目录。崩溃留下的暂存轮次只用于显式检查与清理，不当成已完成备份或自动续传任务。

## 6. HTTP 与本地桥

`/v1/sync/*` 使用独立 `schemaVersion=1` 和封闭 DTO；缺少能力或版本不符时提示更新两端。

| 入口 | 方法 | 职责 |
| --- | --- | --- |
| `/v1/sync/capabilities` | GET | 会话内查询扫描、覆盖、备份和恢复能力及固定预算 |
| `/v1/sync/scans` | POST | 核实本机 rootId，登记异步只读扫描 |
| `/v1/sync/scans/{scanId}` | GET / DELETE | 取状态/结果或取消，轮询不延长期限 |
| `/v1/sync/projects/{projectId}` | GET | 只读取得本机已保存项目的设备 ID 和目录 ID，供发起端核对项目关联 |
| `/v1/sync/jobs` | POST | 接纳方向、扫描和确认计划，服务端复核本机快照、配置和操作集合 |
| `/v1/sync/jobs/{jobId}` | GET / DELETE | 查询实际任务或显式取消 |
| `/v1/sync/jobs/{jobId}/content` | GET / PUT | 按方向提供仅一次的 tar.gz 内容流，边打包边发送；PUT 只接受 chunked 传输 |

这些入口沿用 `x-sync-session-id`、严格 UTF-8/JSON、字节预算和 ID 检查。登记任务需核实保存的游戏映射和对端设备 ID；原生层逐段解析相对路径和根内引用。归档成员仍为 fileId，不直接拼成目标路径。

复制任务使用独立 `SyncJobRequest`：schemaVersion、jobId、sourceProjectId、targetProjectId 和完整 plan；jobId 等于本次 planId，plan.projectId 使用目标端项目 ID。确认后先登记任务，接收端保留本次确认及互斥，登记后立即开始备份，并开始 2 分钟的等待内容计时；拨号方 → 监听方时，监听方在备份或等待内容阶段接收单次 chunked PUT。tar.gz 成员按计划写文件的顺序命名为 `f000001` 起的连续编号，由计划推出，不另传清单。无文件的计划直接执行目录/空计划分支，没有内容。登记或内容回执丢失均只查询同 ID，不重放 POST/PUT。备份或核对先失败时监听方中止接收，上传方得到 `task-conflict`；内容没收齐时任务失败，一项都不写。

监听方 → 拨号方时，监听方的 POST 先返回 preparing，重新扫描源目录并核对与计划一致后进入 ready；内容 GET 只领取一次，监听方边读文件边打包发送。拨号方按确认计划里的备份选择，下载前合并检查缓存、备份和已知同卷的目标增量，然后在写入线程上开始备份，同时下载并边收边解包；备份完成且内容收齐后重新核实目标并写入。写入线程先失败时取消下载。写入器借用拨号方确认时取得的名额及时间；本机处理期间的心跳只核对通信。监听方 sender 的末次查询丢失可单独显示待确认，拨号方仍保留自己的实际写入结果；受保护写入和清理均不重放。

拨号方使用 `x-sync-device-id` 标记既有目录表连接中的设备；它与会话、项目关联和两端目录 ID 一并核对，不作为认证凭据。实际同步请求和进度可更新设备在线时间，避免把持续通信中的传输误记成断连。任务状态分开 sender/receiver、阶段和字节/文件计数；sender 的 sent 仅表示发送完成，目标是否成功仍核对 receiver 的完整 `SyncApplyResult`。预览与结果按需分别查询，避免把两份快照与结果合并到同一控制响应。

保留份数、备份列表与本机恢复通过有限 IPC/Capacitor 桥提供，不开放远端恢复或删除备份的入口。原生任务持有文件、句柄和取消控制，JS 只发确认、取状态及取消；界面卸载不取消任务。文件非空时复用既有 tar.gz/USTAR 规则；仅目录或无需写入的任务走无内容分支，不创建虚构文件或空归档。

## 7. 预算、期限与失败结果

- 每端一个会改目标的活动任务，旧传输、新复制及本机恢复共享互斥；清理未完成时不接纳另一写任务。
- 待传文件最多 1024 个、单文件 256 MiB、原文合计 1 GiB，压缩体/缓存沿用 `BATCH_LIMITS`/`BATCH_RESOURCES`。备份文件独立采用同一文件数/单文件/原文限制，超过任一预算提前拒绝整份计划。
- 计划/控制 JSON 最多 8 MiB；扫描数量/深度另按第 2 节限制。
- 容量预检包含接收缓存、目标卷候选/最终文件增量、目标目录全部文件的备份及轮换前暂时多留一轮的峰值，同卷开销相加。提供者余量未知保持未知，实际写入继续检查；不能提前删除有效备份换空间。
- 总期限 30 分钟、等待内容 2 分钟、网络无进展 60 秒、准备好等待确认及终态保留均最多 10 分钟。重启、会话改变和到期后重扫当前目录，不恢复写任务。
- 分别报告阶段、逐项成功/失败/取消/未执行/待确认、备份及清理状态。`sender sent` 只是已发送，目标成功依据 receiver 回读结果。
- 监听方接收拨号方内容时，拨号方打包期间每秒推送任务摘要：监听方 60 秒没收到摘要，或收到拨号方失败、取消的摘要而内容还没开始上传，就结束接收任务，不等总期限。拨号方失败时发的取消（DELETE）没有收到回应，用户再取消时重发。
- 回执丢失只查询，不重放内容或写入。任务不可查询时标记待确认并提供重读当前目录入口。
