## 1. 基本规则

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 分支命名 | 按项目现有规则执行；没有规则时使用简短英文 kebab-case，表达任务范围。 | `feature/project-memory` |
| 提交信息 | 标题用 `type(scope): 中文描述`；非微小改动写中文正文，说明原因、方案要点、影响范围和验证。 | `feat(设备页): 二维码只带其他设备能访问的地址` |
| PR 描述 | 使用中文概括变更、验证结果、风险和未完成事项。 | `设备页二维码只带可访问地址，补充读取中的状态。` |

## 2. 提交策略

- 以项目开发者的身份写：“用户”只指应用的使用者，不提 Agent、对话或谁提出的要求；以后仍需要人放行的地方写明“维护者”。
- 一个提交应对应一个清晰的阶段成果：功能实现、Bug 修复、测试补充、文档/记忆更新或重构收敛。
- 提交前先查看 `git status` 和 `git diff --stat`，确认只包含本阶段相关文件。
- 提交前尽量运行与本阶段相关的最小验证，并在提交正文或 PR 描述中说明结果。
- 提交信息必须使用中文。标题保持一行且具体，正文写清改了什么、为什么改，让只看 Git 历史的人也能理解。
- 非微小改动必须写提交正文；只改错别字、格式或单行配置时可以只写标题。
- 正文每条只写一个要点，写行为和原因；实现步骤、函数和字段的逐项说明、逐个文件的清单留给 diff。正文一般不超过 10 行。
- 不写工作包、CR 等项目记忆里的编号：条目闭环后会从记忆删除，留在提交历史里就查不到了。
- 不写维护者设备和环境标识（主机名、IP、本机路径、所装软件的产品名、测试数据来自哪台机器），验证只写测试条件。
- `git add`、`commit` 和 `push` 分别需要维护者明确同意；批准计划、实现、做完或收尾不等于同意这些操作，计划或文档里写的提交安排也不算。
- 提交同意默认只覆盖当前工作的一次提交；范围变化或需要 `commit --amend` 时重新确认。
- `push` 须明确远端和分支，不 force-push。合并、rebase、cherry-pick、继续冲突中的 Git 操作和清理分支/worktree 均需维护者单独同意。
- 发布时 main 和 tag 一起推送：`git push --atomic origin main vX.Y.Z`；打 tag 和推送 tag 都要维护者同意，同意里写明 tag 名。只推送 tag、不推送 main 时，发布工作流会因 tag 不在 `origin/main` 上而失败。版本规则见 `docs/development.md` 的“版本号”一节。

## 3. 提交信息格式

```text
<type>(<scope>): <中文描述>

<背景和原因>

技术方案：
- <要点>

影响范围：<受影响的模块或接口>

测试确认：<运行过的检查；没测的场景>
```

- `type` 用英文：`feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。
- `scope` 用中文模块名，可以省略；描述用动宾短语，不加句号。
- 不兼容变更在 `type` 后加 `!`，并在页脚写 `BREAKING CHANGE:` 和迁移方法。

## 4. 正文内容

没有实际内容的段落直接省略，不写“无”：

| 段落 | 内容 |
| --- | --- |
| 背景和原因 | 改之前有什么问题、为什么要改，一两句 |
| 技术方案 | 每条一个要点，写行为和关键取舍；不写 diff 能直接看出的步骤 |
| 影响范围 | 一行列出受影响的模块或接口，不列文件 |
| 测试确认 | 运行过的测试、构建或人工检查，以及没测的场景。写测试条件，不写维护者设备和环境标识；不写项目记忆维护命令 |
