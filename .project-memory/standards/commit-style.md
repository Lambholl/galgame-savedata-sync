## 1. 基本规则

| 类型 | 规则 | 示例 |
| --- | --- | --- |
| 分支命名 | 按项目现有规则执行；没有规则时使用简短英文 kebab-case，表达任务范围。 | `feature/project-memory` |
| 提交信息 | 使用中文标题和必要的中文正文，优先描述阶段成果、原因、验证和风险。 | `记忆策略：完善中文提交说明` |
| PR 描述 | 使用中文概括变更、验证结果、风险和未完成事项。 | `本次完善提交策略并补充验证说明。` |

## 2. 提交策略

- 阶段性完成后应整理差异和验证结果；只有用户明确授权本次提交时才创建本地提交。
- 用户未明确说明授权的有效时间、提交次数或其他范围时，一律视为仅允许当前明确工作包的一次提交；成功创建该提交后授权即耗尽，不自动延续到后续任务、变更或下一次提交。
- 用户明确说明时间、次数或其他范围时，严格按其授权原意和边界执行，不擅自扩展为多次或永久授权；到期、次数用尽、指定范围完成或用户撤销时，授权失效。
- 提交前必须核对用户授权的来源、适用范围和是否仍有效。已完成工作的授权、项目记忆中的旧授权表述、计划正文或 Agent 自行推断，都不能替代当前有效的用户授权。
- 一个提交应对应一个清晰的阶段成果：功能实现、Bug 修复、测试补充、文档/记忆更新或重构收敛。
- 提交前先查看 `git status` 和 `git diff --stat`，确认只包含本阶段相关文件。
- 提交前尽量运行与本阶段相关的最小验证，并在最终回复或 PR 描述中说明结果。
- 提交信息必须使用中文。标题保持一行且具体，正文承担历史追踪职责，避免关键信息只存在临时对话。
- 提交信息的标题（含 scope）、正文和页脚均不得出现具体工作包编号或其变体。使用能力、模块及行为描述变更；工作包编号仅保留在项目记忆和设计文档中，不作为提交范围名或追踪信息写入 message。
- 非微小改动必须写提交正文；只改错别字、格式或单行配置时可以只写标题。
- `git add`、`commit` 和 `push` 分别需要用户明确授权；批准计划、实现、做完或收尾不等于授权这些动作。
- 超出已授权范围、单次授权耗尽后再次提交，或需要 `commit --amend` 时，必须重新取得对应授权；普通提交授权不包含改写已有提交。
- `push` 授权必须明确远端和分支，不包含标签或 force-push。合并、rebase、cherry-pick、继续冲突中的 Git 操作和清理分支/worktree 均需单独授权。

## 3. 提交信息格式

推荐使用中文标题加正文：

```text
记忆策略：完善中文提交说明

变更内容：
- 明确提交信息必须使用中文标题和中文正文
- 补充变更原因、验证结果、风险和后续事项的记录要求

变更原因：
- 项目记忆只保存当前态，需要由 Git 提交信息承担历史追踪职责

验证结果：
- npm test 通过
- npm run validate:skill 通过

风险与后续：
- 旧项目如已有自己的提交规范，应以项目级规范为准
```

需要表达范围时，可以使用中文范围前缀：

```text
记忆模板：完善提交规范
```

## 4. 正文内容

非微小改动的正文至少包含：

| 段落 | 内容 |
| --- | --- |
| 变更内容 | 本次实际完成了什么，按功能、文档、测试、配置等归类 |
| 变更原因 | 为什么需要改，关联需求、问题、风险或决策 |
| 验证结果 | 运行过哪些测试、校验或人工检查；无法验证时说明原因 |
| 风险与后续 | 兼容风险、未覆盖场景、需要用户继续确认或后续处理的事项 |

避免使用空泛信息：

```text
更新
修改文件
fix
wip
```

避免只写英文或只写过短标题：

```text
update project
fix hooks
docs
```
