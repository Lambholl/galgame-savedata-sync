# 注释规范

适用于所有语言的代码注释。项目差异写在[编码规范](coding-style.md)的“代码注释”一节。

- 所有语言的说明性注释统一使用中文，包括行注释、块注释及接口文档注释（Javadoc、JSDoc/TSDoc、XML documentation、docstring 等）；配置文件和文档代码示例中的说明性注释同样适用。
- 代码标识、API 名称、标准术语、URL、文档标签和工具识别的指令保留原文；注释中的说明文字使用中文。第三方版权及许可声明保留原文。
- 函数和类的注释先说明功能：做什么、操作什么数据、返回什么。“仅、只、始终、绝不”这类限定句和边界条件都不能代替功能说明。
- 功能说明之后，再补充读代码看不出的业务规则、边界条件、安全和隐私约束、非显然算法和兼容性取舍。
- 行内注释写原因和后果，如“SAF 的 deleteDocument 会递归删除，这里先确认文件夹是空的”。
- 避免把显而易见的语句改写成注释。
- 注释写给第一次读这段代码的维护者：用完整的句子和代码里查得到的名称，写明具体是什么数据、什么期限、由谁调用。不用自造简称和压缩句（如“原生目标任务”“重扫”“预算”），不用斜杠堆名词，分号不用来挂否定分句。
- 术语要能在代码或[项目术语表](../project/glossary.md)里查到，同一个词不表示两种东西。
- 不用“新、旧、现有、既有、本轮”指代模块，写类名或函数名。不写工单号。
- 不写代码没做什么。没有实现的功能、已移除的逻辑和别处已规定的范围（如“不启动保活服务”）不写进注释；范围决定放需求或架构文档，移除原因放提交信息。限制写成事实，如“结果在扫描结束 10 分钟后清除”，不写“查询不刷新结果期限”。
- 不写给评审者看的自证，如“冒充、伪造、包装、承诺、声称、替代”这类话。限制是真实的，就写会发生什么，如“两次检查之间文件可能被替换”。
- 不为不存在的调用方、测试或场景写说明。
- 不用注释掩盖混乱实现；应优先改善命名、拆分函数或调整结构。
