## 1. 长期测试范围

长期自动化测试只覆盖稳定的基础边界：API 输入输出、数据模型、持久化、文件安全和少量跨端核心结果。可以保留的范围包括：

- API 的输入、输出、错误码和协议版本。
- 数据转换、持久化、文件读写边界和跨端角色。
- 难以人工重复的核心纯逻辑。
- 两个平台实现不同、必须分别确认的基础行为。

界面细节用实际操作或截图验收，包括按钮、组件树、DOM 选择器、页面文案、弹窗、布局、CSS 和颜色。临时自动化检查确认后删除，不提交快照测试。

界面改版、文案调整和组件重构可以独立变化，长期测试不依赖这些细节。某个稳定 API 只有通过界面才能触达时，把逻辑移到服务或状态模块，测试 API。

具体业务场景可以在开发时临时测一次，确认后删除临时断言，不进入长期套件。长期测试保留的是接口和数据边界，不保留某次需求下的页面流程。

同一条规则在一个合适的层级验证。共享校验覆盖后，平台测试检查平台特有的 I/O、权限、路径和生命周期；集成测试覆盖关键流程，已经由下层验证的失败场景不再重复。

## 2. 新增与删除

默认不新增或扩写自动化测试，用户在当前任务明确要求时才编写长期测试。实现功能、修复 bug、重构和清理代码都不构成测试授权。

发现以下情况时，直接删除或合并：

- 测试界面设计和具体文案。
- 重复验证下层已经覆盖的规则。
- 验证第三方框架、语言或系统自身的行为。
- 只检查内部调用顺序、私有字段或日志文本。
- 测试一套已完成的实验、基准或模板代码。
- 需求变化后已经失效的旧断言。

高风险回归需要新测试时，先向用户说明风险、准备验证的场景、预计测试代码行数，以及现有检查哪里不够。获得明确同意后再写。

不设覆盖率目标，不要求每个分支、字段组合或失败排列都有用例。测试失败时先判断产品回归还是需求变化；需求变了就删旧断言，不为让测试通过扩大覆盖。

## 3. 测试写法

- 测试名写一个行为和结果，例如“下载返回目标文件”。
- 一个用例围绕一个场景；断言集中在公开 API 的输出、错误和副作用。
- 测试公开边界，不依赖私有函数、内部调用次数或实现步骤。
- Mock 只替代真实外部依赖、设备或受控故障；内部业务路径直接执行。
- 类型约束交给 `tsc`。不默认维护 `@ts-expect-error` 类型反例套件。
- 文件名沿用包内现有约定，Node 测试使用 `.test.mjs`，Java 测试使用 `*Test.java`。

## 4. 验证方式

按以下顺序选择验证，够用就停：

1. 文本、格式、lint、类型检查和构建。
2. 实际操作、运行程序或截图。
3. 最小相关既有测试。
4. 全量测试，仅用于发布前、大范围高风险改动或用户明确要求。

`pnpm check` 执行静态检查和构建。全量测试走 `pnpm test:all`，日常检查和普通 CI 不运行它。Android 原生测试在改动相关原生代码、准备发布或用户明确要求时运行。

## 5. 记录方式

测试记录保存未解决的回归、验收场景和可复验入口；用例数量、单次运行输出和逐条断言交给 Git 与测试输出。已经通过且能从代码直接看出的细节不逐项抄进项目记忆。
