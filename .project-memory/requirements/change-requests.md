# 变更请求

保留还没完整吸收到当前需求、范围或架构的变更，以及实现、验证、迁移或外部依赖仍有缺口的变更。结论完全吸收且没有缺口后删除对应行，由 Git 保存历史。

| ID | 变更 | 原因 | 影响 | 状态 |
| --- | --- | --- | --- | --- |
| CR-024 | 传输流程精简。① 比较只看类型、大小和修改日期，日期相差 2 秒内算相同，扫描不再读取文件内容；写入后把目标文件的修改日期设为来源的修改日期，写不了日期的目标（Android 未授予所有文件访问权限、走 SAF）下次比较显示“不同”，提示可开启所有文件访问权限。② 计划、清单、备份清单和协议去掉 SHA-256；完整性由 TCP、gzip 的 CRC32 与长度、tar 结构和清单中的文件大小保证，出错时失败并提示重试。③ 发送端读源文件时直接流式打包写入 HTTP 请求体，不再先复制到私有缓存、不再把压缩包落盘；读完一个文件后核对大小和修改日期，变化时本次失败。④ 接收端登记任务后立即开始备份，与发送端读取、传输并行。⑤ 接收端边收边解包：电脑和 Android 直接读写时写成目标旁的临时文件，全部收完且备份完成后逐个改名替换；Android 走 SAF 时先解包到私有目录，之后按现有方式原地写入目标，因为 SAF 每次打开文件约 29 ms，新建、删除、改名会把逐文件开销翻几倍，且 SAF 改名不能覆盖已有文件。网络中断或数据不完整时目标不变。⑥ 进度改为备份、传输（并行）和写入三段，去掉打包、校验两段。⑦ 协议版本升级，不兼容旧版本，两端版本不一致时提示升级 | 原流程为每个文件至少计算 4 次 SHA-256、压缩包整体再计算 3 次，同一份数据在两端私有缓存和磁盘上反复读写，备份排在接收和校验之后才开始；局域网 TCP 已保证数据完整，偶发错误重试即可 | REQ-015、REQ-018、REQ-020 的验收标准，架构总览 3.2/3.3，接口约定中 content 上传的长度与哈希头，`docs/plans/m001-tar-gzip-protocol.md`；两端扫描、打包、接收、备份、写入、恢复和进度展示；TC-014、TC-015、TC-036 等传输用例需重做。Android 直接读写时 `File.setLastModified` 能否生效待真机确认 | accepted |
