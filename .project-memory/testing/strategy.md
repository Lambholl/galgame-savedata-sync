## 1. 验证目标

验证要回答两个问题：功能是否按当前需求工作，以及数据是否会丢失或写错。

自动化测试覆盖长期稳定的边界：

- API 输入、输出和错误码。
- 数据结构、归档格式和跨平台协议。
- 文件读写、持久化和发布边界。
- 难以人工重复的核心纯逻辑。

按钮、页面文案、DOM 结构、CSS、颜色、布局和截图用浏览器或设备做界面验收。临时检查代码确认后删除。

具体业务场景可以在当前任务中临时验证一次，确认后删除；长期套件只保留接口、数据和文件边界。

## 2. 默认验证顺序

1. 格式、lint、类型检查和构建。
2. 实际运行、ADB 操作或截图。
3. 最小相关既有测试。
4. 全量测试，仅用于发布前、大范围高风险改动或用户明确要求。

`pnpm check` 执行静态检查和构建。`pnpm test:all` 用于发布或高风险改动，不进入日常检查。`pnpm android:test` 用于相关原生改动和发布前检查。

## 3. 边界

默认不新增或扩写自动化测试。用户在当前任务明确要求时才可以写测试；高风险回归确实需要新增测试时，先说明风险、验证场景和预计代码行数。

同一规则在一个合适层级验证。共享层覆盖数据约束后，平台测试检查本平台特有的权限、路径、I/O 和生命周期；集成测试覆盖关键流程。

界面改版和文案变化可以独立发生，长期测试不依赖这些细节。某个稳定 API 只有通过界面触达时，把逻辑移到服务或状态模块，测试 API。

不设覆盖率目标，每个字段、分支或失败组合都不需要单独写用例。需求变化后直接删除过时断言。

## 4. 记录

测试记录保存当前验收场景、未解决回归和复验入口。测试数量、单次运行输出和逐条断言说明由 Git 与测试输出保存。
